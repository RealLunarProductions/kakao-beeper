# kakao-beeper on macOS — notes for Claude Code

You are looking at the install package (or the installed copy) of **kakao-beeper**, a
self-hosted bridge that puts a person's KakaoTalk chats into their Beeper account. This
file tells you how it is put together, where things live on this Mac, how to diagnose
it, and which lines not to cross. The human-facing instructions are in `README.md`.

```
Beeper (cloud)  <--outbound websocket--  mautrix-kakaotalk (Go, bridgev2)
                                              |  JSON lines over stdio
                                         sidecar.mjs (Node)  --LOCO (TLS)-->  KakaoTalk
```

- The Go bridge is a [mautrix-go bridgev2](https://pkg.go.dev/maunium.net/go/mautrix/bridgev2)
  connector (`src/pkg/connector`). It talks to Beeper over an **outbound** websocket
  (`homeserver.software: hungry`); nothing listens on a port, so no firewall rule is needed.
- The sidecar (`sidecar/sidecar.mjs`) holds one KakaoTalk LOCO session through the npm
  package [agent-messenger](https://github.com/agent-messenger/agent-messenger), signed in as
  the account's **tablet** device. Protocol: request `{"id","method","params"}` → response
  `{"id","result"|"error":{"code","message"}}`; events `{"event","data"}` (`message`, `read`,
  `connected`, `disconnected`, `kicked`, `fatal`, `error`, `member_joined`, `member_left`).
- Unofficial: this uses KakaoTalk's device protocol, which Kakao's terms don't allow. The
  owner of the account accepted that risk when installing; don't widen it (see Hard rules).

## Where everything is after `install.sh`

| Path | What |
| --- | --- |
| `~/.local/share/kakao-beeper/` | data dir (`$KAKAO_BEEPER_DATA` overrides) |
| `  app/bin/mautrix-kakaotalk` | the bridge binary (arm64 or amd64, matching the CPU) |
| `  app/bin/bbctl` | Beeper's bridge manager, pinned version + sha256 in `install.sh` |
| `  app/sidecar/` | `sidecar.mjs` + `node_modules` (`npm ci --omit=optional`) |
| `  app/node/` | our own Node.js, only if no Homebrew/official Node ≥ 22.13 was found |
| `  app/node-path` | the node binary the config points at |
| `  config.yaml` | generated by `bbctl config --type bridgev2 sh-kakaotalk`, plus a `network:` section appended by `kakao-beeper configure` (`node_path`, `sidecar_script`, `state_dir`, `initial_backfill`) |
| `  sh-kakaotalk.db` | sqlite: Beeper room ↔ KakaoTalk chat mapping, message IDs, crypto keys |
| `  agent-messenger/` | the sidecar's private copy of the KakaoTalk credentials + sync state |
| `  logs/bridge.log` | JSON lines (zerolog), rotated by the bridge; `logs/launchd-stderr.log` = anything printed before logging is up |
| `  network-icon.txt` | cached mxc URI of the uploaded KakaoTalk icon |
| `~/.config/agent-messenger/kakaotalk-credentials.json` | KakaoTalk tablet-device credentials written by `auth login` (mode 600) |
| `~/Library/LaunchAgents/com.kakao-beeper.bridge.plist` | login item; `RunAtLoad`, `KeepAlive` unless clean exit, `WorkingDirectory` = data dir |
| `~/.local/bin/kakao-beeper` | the control script (bash 3.2 compatible) |
| bbctl's own state | wherever bbctl keeps it (`bbctl whoami` shows the login) |

Package layout (before install): `install.sh`, `kakao-beeper`, `README.md`, `sidecar/`
(script + lockfile), `src/` (Go source), `bin/` (prebuilt binaries, if the package has them),
`VERSION`.

## Operating it

```
kakao-beeper status      launchd state + last bridge state + sign-ins + last log lines
kakao-beeper doctor      every link checked, OK/FAIL with the fix for each FAIL
kakao-beeper logs        tail -f of bridge.log and launchd-stderr.log
kakao-beeper restart | stop | start | enable | disable
kakao-beeper login-kakao | login-beeper | configure | setup | uninstall
```

Direct launchd equivalents: `launchctl print gui/$(id -u)/com.kakao-beeper.bridge`,
`launchctl kickstart -k gui/$(id -u)/com.kakao-beeper.bridge`,
`launchctl bootout gui/$(id -u)/com.kakao-beeper.bridge`, `launchctl bootstrap gui/$(id -u) <plist>`.
"Bootstrap failed: 5: Input/output error" means it is already loaded — bootout first.

Reading the log: it is JSON per line. Useful filters:
`grep '"bridge_state"' logs/bridge.log | tail -1` (current state Beeper sees — look at
`state_event` and `error`), `grep -E '"level":"(error|warn)"'`, `grep sidecar_stderr`
(the sidecar's own messages are relayed at debug level under that key).

What healthy looks like: `state_event":"CONNECTED"` as the last bridge state, "Syncing
chats" shortly after start, and incoming messages logged as `RemoteEventMessage`. The
bridge sends a CHATINFO round trip every 90 s as a health check — that is normal traffic.

## Connection behaviour (so you don't misdiagnose it)

- The sidecar **reconnects by itself** after a socket close (sleep, Wi-Fi change) with a
  3 s → 60 s backoff, then the bridge resyncs chats and forward-backfills what was missed.
  A `TRANSIENT_DISCONNECT (kakao-disconnected)` state that clears within a minute of the
  network returning is normal.
- A failed start while offline is retried: 10 s, 20 s, 40 s … capped at 5 min
  (`kakao-start-failed`). It is **not** a credentials problem.
- `kakao-kicked`: another device signed in to the tablet slot (an iPad, an Android tablet,
  or the `agent-kakaotalk` CLI). The sidecar exits with code 3 and the bridge signs in
  again after one minute — which kicks the other device back. If the person wants the
  other device, `kakao-beeper stop` (or `disable`) while they use it.
- `BAD_CREDENTIALS (kakao-login-failed)`: KakaoTalk rejected the token (sidecar exit code
  78). The bridge stops retrying. Fix: `kakao-beeper login-kakao`, then `kakao-beeper restart`.
- Only one LOCO connection per device exists. Running `agent-kakaotalk` (the CLI the
  credentials came from) while the bridge is up kicks the bridge. Use Beeper instead.

## Diagnosis playbook

Start with `kakao-beeper doctor`; it names the fix for each failing check. Beyond that:

| Symptom | Look at | Fix |
| --- | --- | --- |
| `kakao-beeper: command not found` | `~/.local/bin` not on PATH | run `~/.local/bin/kakao-beeper`, or add `export PATH="$HOME/.local/bin:$PATH"` to `~/.zshrc` |
| nothing in Beeper after setup | did they DM `@sh-kakaotalkbot:beeper.local` with `login`? `status` shows no bridge state | send `login` to the bot in Beeper Desktop |
| "bad CPU type in executable" | wrong-arch binary (Rosetta terminal confuses `uname -m`) | `install.sh` picks the arch via `sysctl hw.optional.arm64`; re-run it |
| binary "killed" at start, or Gatekeeper dialog | quarantine flag / unsigned | `install.sh` runs `xattr -dr com.apple.quarantine` + ad-hoc `codesign` on `app/bin`; re-run it |
| `launchctl bootstrap` → "5: Input/output error" | already loaded | `kakao-beeper restart` (does bootout+bootstrap) |
| sidecar won't start, `node: bad option` / `ERR_MODULE_NOT_FOUND` | wrong node or missing node_modules | `app/node-path` must be ≥ 22.13; re-run `install.sh --no-setup` |
| `config.yaml isn't a Beeper config` | a default config was generated by the bridge itself | `kakao-beeper configure` moves it aside and regenerates via bbctl |
| `bbctl config` fails | not signed in, or the name is taken by another self-hosted bridge on that Beeper account | `kakao-beeper login-beeper`; `bbctl` lists bridges |
| build from source fails | no Go / no command line tools | `brew install go`, `xcode-select --install`; the Go toolchain in `go.mod` auto-downloads if Homebrew's is older |
| `npm ci` fails with lockfile errors | npm older than the lockfile version | use the Node the installer downloads (`rm -rf app/node` first), re-run |
| photos from Beeper rejected | only `image/jpeg` and `image/png` are accepted; captions are rejected | expected; see room capabilities in `chatinfo.go` |
| mass duplicate rooms in Beeper | someone deleted `sh-kakaotalk.db` | don't delete it; if it happened, `bbctl delete sh-kakaotalk` and set up again |

## Adapting to this person's Mac

- **Another data location**: `KAKAO_BEEPER_DATA=/path kakao-beeper …` (and the same env for
  `install.sh`). The plist bakes the path in — re-run `kakao-beeper enable` after moving.
- **A specific Node**: `KB_NODE=/path/to/node bash install.sh`. It must be a real binary at
  a stable path; version-manager shims (nvm, volta, asdf, fnm) don't work under launchd.
- **No Homebrew**: fine. The installer downloads the official Node build (sha256-checked)
  and the official bbctl release; only building from source needs Go + command line tools.
- **Several macOS users**: everything is per-user (`~`, `gui/<uid>`); install per user.
- **Intel Mac**: supported (`amd64`); prebuilt binaries ship for both when the package has them.
- **Corporate proxy / filtered network**: the bridge needs `matrix.beeper.com:443` (websocket),
  `*.kakao.com` (LOCO booking on 443, checkin on 995, then a chat server port the booking
  step returns) and `talk.kakaocdn.net` for media. A proxy that blocks non-HTTP ports stops it.
- **Run only while Beeper is open**: not supported; it is a login item so chats keep syncing
  (and reach Beeper on their phone) while the Mac is awake.
- **Updating**: unpack the new package, `bash install.sh --no-setup`, `kakao-beeper restart`.
  Data, config and sign-ins are kept. Pinned versions to bump in `install.sh`:
  `NODE_VERSION`, `BBCTL_VERSION` + the two `BBCTL_SHA_*` from the release's `sha256sums.txt`.
- **Source changes**: Go in `src/`, build with `-tags goolm` (pure-Go olm; without it cgo
  wants libolm). The sidecar's exit codes (3 kicked, 78 bad credentials) and event names
  are a contract between `sidecar.mjs` and `src/pkg/connector/client.go` — change both.

## Hard rules

1. **Never** sign in with `--device-type pc` or `--force`. PC would sign out their KakaoTalk
   desktop app; force kicks whatever holds the slot. The tablet slot is the deal.
2. **Never** enter, store, script or read back their KakaoTalk password or the phone
   passcode. The person types them into `kakao-beeper login-kakao` themselves. Don't pass
   `--password`/`--password-file`, and don't look inside `kakaotalk-credentials.json`.
3. **Never** send a KakaoTalk message on their behalf (via Beeper, bbctl or the CLI)
   unless they approve that exact message. Drafting in Beeper is fine; sending is theirs.
4. Don't copy, commit, or paste credentials, `config.yaml` (it holds the Beeper
   appservice tokens), or `sh-kakaotalk.db` anywhere.
5. Don't delete `sh-kakaotalk.db` or `agent-messenger/` to "reset" something; see the
   playbook. `kakao-beeper uninstall` is the only sanctioned wipe, and the person confirms it.
6. Don't run `agent-kakaotalk` CLI commands while the bridge is up (same device → kicks).
7. Don't weaken the install: keep the sha256 checks on downloads and the pinned versions.
